# 문제를 구현으로 연결한 사례

저는 프론트엔드와 PM을 맡아 입력 조건·API 처리 상태·일정 편집을 하나의 사용자 흐름으로 연결했습니다. 아래는 실제 코드와 테스트로 확인할 수 있는 판단입니다. 실사용자 지표나 운영 장애 해결 성과로 확대하지 않았습니다.

## 1. AI 요청의 ‘접수’와 ‘완료’를 나눴습니다

### 문제

일정 생성 요청이 접수돼도 결과가 즉시 만들어지는 것은 아닙니다. 접수 응답을 완료로 처리하면 아직 없는 일정을 보여주거나, 기다리는 동안 무슨 일이 일어나는지 설명하기 어렵습니다.

### 제가 선택한 방법

저는 생성 요청과 상태 조회를 API 경계에서 연결했습니다. `requestTripPlan`은 접수 후 `PENDING`·`PROCESSING`을 기다리고, `COMPLETED`의 결과만 화면 모델로 변환합니다. 실패·알 수 없는 상태·시간 초과·취소는 결과와 구분합니다.

백엔드 담당자와 이 상태 계약을 맞췄고, 팀은 API와 Worker를 SQS로 분리했습니다. **프론트의 대기 흐름은 제가 담당했고, 서버 비동기 처리는 팀 구현입니다.**

### 확인 가능한 근거

- [프론트 요청·polling·응답 변환](../frontend/src/api/tripPlanApi.js)
- [접수 → PROCESSING → COMPLETED 회귀 검사](../frontend/tests/tripPlanPolling.test.mjs)
- [팀의 작업 접수](../backend/src/main/java/com/travel/trip/plan/async/TripPlanRequestService.java), [Worker](../backend/src/main/java/com/travel/trip/plan/async/TripPlanWorker.java)

상태 조회는 기본 2초 간격이며 무한히 기다리지 않도록 전체 제한을 둡니다. 이 간격은 코드의 설정값이며, 운영 환경에서 최적이라고 측정한 값은 아닙니다.

## 2. 같은 항공 검색은 공유하되, 취소와 세션은 분리했습니다

### 문제

같은 검색 조건으로 여러 조회가 겹치면 중복 요청이 생길 수 있습니다. 반대로 모든 요청을 한꺼번에 공유하면 한 요청의 취소나 로그인 계정 변경이 다른 결과에 영향을 줄 수 있습니다.

### 제가 선택한 방법

저는 검색 조건별 진행 중 요청을 공유하고, 완료 결과는 1분 동안 재사용하도록 구성했습니다. 반환값은 복제해 호출자가 다른 호출자의 데이터를 바꾸지 않게 했습니다. 오류·빈 결과는 재조회할 수 있게 유지하고, 세션이 바뀌면 이전 결과를 비웁니다. 명시적인 `AbortSignal`이 있는 요청은 취소 책임을 보존하기 위해 별도로 실행합니다.

### 확인 가능한 근거

- [항공 검색 어댑터](../frontend/src/api/flightApi.js)
- [중복·만료·실패 재시도·세션 변경·개별 취소 검사](../frontend/tests/flightSearchCache.test.mjs)

이 결과로 실제 서버 비용이나 응답 시간이 몇 퍼센트 줄었다는 운영 측정값은 제시하지 않았습니다. 테스트는 정의한 조건에서 요청 공유와 데이터 분리가 지켜지는지 확인합니다.

## 3. 화면에서 바꾼 순서와 서버에 저장할 순서를 구분했습니다

### 문제

화면에는 원본 일정 외에 이동·항공 등의 표시 카드가 합쳐질 수 있습니다. 보이는 배열을 그대로 저장하면 고정 항공편·숙소 위치나 원본 일정의 식별자가 바뀔 수 있습니다. 화면의 수정 초안과 서버 저장 완료를 같은 상태로 취급해서도 안 됩니다.

### 제가 선택한 방법

저는 화면 표시 순서에서 원본 일정의 식별자를 찾아 편집 요청으로 변환했습니다. 고정 항목은 유지하고 편집 가능한 항목만 재정렬하며, 순서가 바뀌면 서버가 시간을 다시 계산할 수 있게 요청을 구성합니다.

저장 요청에는 `requestId`·`baseRevision`을 함께 전달합니다. 백엔드 담당자는 소유권과 revision을 검사하고, 변경된 날짜의 경로·시간·비용을 계산해 저장합니다. 저는 이 계약에 맞춰 화면의 요청과 결과를 연결했습니다.

### 확인 가능한 근거

- [편집 payload 구성](../frontend/src/utils/planEditPayload.js)
- [고정 일정 보존·편집 순서 검사](../frontend/tests/planEditPayload.test.mjs)
- [로컬 편집 초안](../frontend/src/planner/planDraftEdits.js), [저장 API](../frontend/src/api/planEditorApi.js)
- [팀의 소유권·revision·변경 날짜 저장](../backend/src/main/java/com/travel/trip/plan/edit/PlanEditService.java)

현재 서버 편집은 **항공 + 렌터카 여행**을 지원합니다. 다른 교통수단의 로컬 미리보기나 시연 데이터까지 서버 저장이 완료된 것처럼 설명하지 않습니다.
