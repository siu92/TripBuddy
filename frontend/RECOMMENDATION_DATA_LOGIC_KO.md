# TripBuddy 데이터·필터링·일정 생성 로직 요약

이 문서는 현재 프론트엔드와 백엔드 코드가 실제로 동작하는 방식을 기준으로 정리한 설명서입니다. 발표에서는 아래의 **쉽게 말하면** 문장을 중심으로 설명하면 됩니다.

## 1. 전체 흐름

1. 사용자가 출발지, 목적지, 날짜, 인원, 교통수단, 숙소, 테마, 여행 속도와 선호 음식을 선택합니다.
2. 각 영역에서 실제 데이터로 만든 후보를 먼저 좁힙니다.
3. 거리만 가까운 장소가 아니라 평점·리뷰·대표성·취향·날씨를 함께 점수화합니다.
4. Amazon Bedrock의 `Nova Lite`가 정리된 후보 안에서 날짜별 순서를 구성합니다.
5. 카카오모빌리티의 실제 도로 이동시간을 우선 반영해 동선을 다시 계산합니다.
6. 항공·식사·숙소처럼 시간이 정해진 일정을 보호하면서 긴 빈 시간을 보완합니다.
7. 사용자가 일정을 바꾸면 이동시간, 도착시간과 예상 경비를 다시 계산합니다.

**쉽게 말하면:** AI가 아무 장소나 지어내는 방식이 아니라, 먼저 검증된 실제 장소 후보를 만들고 그 안에서 이동 가능한 조합을 고르는 방식입니다.

## 2. 숙소

### 데이터 출처

- 원천 숙박업 목록은 공공데이터포털의 행정안전부 **숙박업**과 **관광숙박업** API를 적재합니다.
- 같은 숙소가 두 원천에 중복될 때는 연결된 상세 정보, 좌표, 도로명 주소가 있는 항목을 우선해 하나로 합칩니다.
- 실제 추천 화면은 원천 목록을 그대로 노출하지 않습니다. `NAVER_HOTEL`로 상세 정보가 연결된 `accommodation_enrichment` 데이터에서 숙소명, 주소, 좌표, 평점, 리뷰 수, 대표 이미지, 체크인·체크아웃, 평균 가격을 사용합니다.

### 추천 기준

- 좌표가 있는 숙소만 추천 후보가 됩니다.
- 사용자가 선택한 목적지를 중심으로 우선 **예상 차량 30분 이내**를 찾습니다.
- 후보가 부족하면 **45분 이내**, 그래도 부족하면 제주 전체로 범위를 넓힙니다.
- 최종 점수는 평점과 리뷰 수를 함께 본 신뢰도 65%, 목적지와의 이동 편의 35%입니다.
- 리뷰가 몇 개뿐인 높은 평점이 과도하게 올라가지 않도록 전체 평균과 리뷰 수를 함께 반영합니다.

### 가격 필터와 예산

- 화면 가격대는 5만원 미만, 5만~10만원, 10만~20만원, 20만~30만원, 30만원 이상으로 나눕니다.
- 특정 가격대를 선택하면 평균 가격이 없는 숙소는 제외합니다.
- 가격순에서는 평균 가격이 없는 숙소를 뒤로 보냅니다.
- 숙박비는 `평균 1박 가격 × 숙박 수 × 객실 수 ÷ 인원`으로 1인 예상액을 계산합니다.

**쉽게 말하면:** 원천 숙소 수가 많더라도 화면에는 위치와 상세 정보가 확인된 숙소만 올리고, 목적지에서 너무 멀지 않으면서 리뷰 신뢰도가 높은 곳을 먼저 보여줍니다.

### 수량 표현 시 주의

공공 원천 데이터의 전체 적재 건수와 실제 추천 가능한 숙소 수는 같은 숫자가 아닙니다. 중복 제거, 상세 정보 연결, 좌표 확인을 거치면서 추천 후보가 줄어듭니다. 따라서 발표에서 “약 6만 개의 원천 숙박 데이터를 수집했다”라고 설명할 수는 있지만, “화면에서 6만 개를 그대로 비교한다”라고 표현해서는 안 됩니다. 실제 운영 DB 건수는 배포 직전 별도로 조회해 확정해야 합니다.

## 3. 관광지

### 데이터 출처

- 제주 관광지는 제주 공식 관광 정보인 `VISIT_JEJU` 제공 데이터를 사용합니다.
- 관광지 이름, 권역, 주소, 좌표, 태그, 소개, 대표 이미지를 후보 판단에 사용합니다.
- 프론트의 제주 대표 명소 15곳도 실제 장소명과 WGS84 좌표를 갖고 있으며, 선택한 장소는 일정에 반드시 한 번 포함됩니다.

### 1차 제외 기준

- 좌표가 없는 장소는 제외합니다.
- 협의회, 운영위원회, 주민센터, 사무소, 마을회관, 복지회관, 자치회, 영농조합, 영어조합, 개발위원회처럼 관광 목적이 불분명한 행정·단체 시설은 제외합니다.
- 대표 명소이거나, 사진이 있거나, 충분한 소개가 있는 장소만 여행자가 방문할 수 있는 후보로 인정합니다.

### 추천 점수

- 지역 대표성 25%
- 사진·소개·태그 등 정보 완성도 20%
- 사용자가 고른 관광·액티비티 등의 취향 25%
- 날씨 적합도 10%
- 여행 속도 적합도 10%
- 이동거리 10%

성산일출봉, 한라산, 우도, 섭지코지, 주요 폭포·해변·오름·수목원 등 제주를 대표하는 장소는 대표성 점수를 받습니다. 가까운 무명 장소가 유명 명소보다 무조건 앞서는 문제를 막기 위해 거리 비중은 10%로 제한했습니다.

**쉽게 말하면:** 가까운 곳부터 채우는 일정이 아니라, 제주에 갔다면 만족도가 높은 대표 명소를 먼저 고르고 그 안에서 이동 가능한 동선을 만듭니다.

## 4. 식당

### 데이터 출처

- 식당 DB에는 카카오 장소 ID, 실제 장소명, 업종, 주소, 좌표, 장소 링크, 평점, 리뷰 수, 영업시간, 대표 이미지와 메뉴 정보가 저장됩니다.
- 활성 메뉴만 사용하고 추천 메뉴를 먼저 표시합니다.
- 화면의 식비는 수집된 메뉴 가격을 바탕으로 계산하지만, 업체와 실시간 가격 제휴를 맺은 값은 아니므로 예상 금액입니다.

### 1차 제외와 취향 필터

- 좌표가 없는 식당은 제외합니다.
- 수집 상태가 실패, 폐업 또는 영구 폐업인 식당은 추천 후보에서 제외합니다.
- 사용자가 고른 한식·양식·일식 등의 음식 취향을 업종과 연결해 먼저 후보를 좁힙니다.
- 신뢰할 만한 후보가 충분하면 평점 3.5 이상이면서 리뷰 10개 이상이거나, 리뷰가 100개 이상인 식당을 우선 후보군으로 사용합니다.

### 추천 점수

- 평점과 리뷰 수를 함께 본 신뢰도 55%
- 제주 향토 음식·지역 특색 15~20%
- 거리 10~15%
- 이미지·영업시간·설명 등 정보 신뢰도 15%

맛집 테마에서는 거리보다 제주 음식과 장소 품질의 비중을 높입니다. 아침에는 국밥·죽·국수·김밥처럼 자연스러운 메뉴를, 저녁에는 흑돼지·구이·회처럼 저녁에 어울리는 메뉴를 우선하도록 식사 시간대 적합도도 계산합니다.

**쉽게 말하면:** 평점 숫자만 보는 것이 아니라 리뷰가 충분한지, 지금 시간대에 먹기 좋은 메뉴인지, 제주에서 먹을 이유가 있는지까지 함께 봅니다.

## 5. 카페

- 카페 DB도 카카오 장소 ID, 좌표, 평점, 리뷰 수, 이미지, 영업시간, 설명, 태그와 메뉴를 사용합니다.
- 일반 여행은 15분 이내, 후보가 부족하면 25분 이내로 넓힙니다.
- 맛집·카페 테마에서는 30분, 부족하면 45분까지 허용합니다.
- 일반 일정은 평점·리뷰 65%, 거리 15%, 오션뷰·디저트·정원 같은 카페 경험 20%입니다.
- 음식 중심 일정은 평점·리뷰 60%, 거리 10%, 카페 경험 30%로 특색을 더 강하게 반영합니다.

## 6. 서울 → 애월 카페 거리 시나리오

- 출발지는 서울 행정구역 좌표를 사용합니다.
- 목적지는 `애월 카페 거리`, 위도 `33.4635`, 경도 `126.3094`로 전달합니다.
- 띄어쓰기나 `제주특별자치도` 접두어가 달라도 백엔드가 같은 장소로 인식합니다.
- 사용자가 선택한 목적지는 일반 추천 후보보다 우선하는 필수 장소이며, 일정 전체에서 정확히 한 번 포함됩니다.
- 제주 대표 명소 15곳 모두 같은 이름·좌표 검사를 자동으로 통과해야 운영 빌드를 완료할 수 있습니다.
- 숙소·식당·카페 후보에는 선택 숙소 기준 이동정보와 목적지 기준 이동정보가 함께 붙습니다.

## 7. 최종 일정 생성과 빈 시간 보정

- 최종 일정 편성에는 Amazon Bedrock의 `apac.amazon.nova-lite-v1:0`을 사용합니다.
- AI에는 모든 DB를 그대로 주지 않고, 앞 단계에서 점수를 통과한 관광지·식당·카페 후보만 전달합니다.
- 필수 목적지, 왕복 항공 시간, 렌터카 인수·반납, 숙소, 식사 시간대를 먼저 보호합니다.
- 카카오모빌리티 실제 도로 거리·시간이 있으면 직선거리 추정보다 우선합니다.
- 일정 사이 빈 시간이 75분 이상이면 다음 일정에 늦지 않는 범위에서 추천 장소를 최대 두 곳까지 검토합니다.
- 한 번에 너무 많은 장소를 넣지 않도록 한 공백당 최대 두 곳으로 제한하고, 각 추가 장소 뒤에도 다음 장소까지 실제 이동 가능한지 다시 확인합니다.
- 첫날에는 체크인만 하려고 숙소를 중간에 들렀다가 다시 나오는 비현실적인 동선을 피하고, 가능한 경우 저녁 일정 뒤 숙소에 도착합니다.

Tripadvisor가 실제 여행자 리뷰·평점·인기도를 추천 근거로 쓰고 사용자가 일정을 편집할 수 있게 하는 방식, Wanderlog가 하루 경로를 이동시간 중심으로 최적화하는 방식을 참고했습니다. TripBuddy는 여기에 예산과 상세 경비, 필수 목적지, 국내 교통수단을 함께 결합했습니다.

참고: [Tripadvisor AI Trip Builder](https://www.tripadvisor.com/AIAssistant), [Wanderlog route optimization](https://help.wanderlog.com/hc/en-us/articles/13545624787867-Optimize-route)

## 8. 실제 데이터와 예상·목업 데이터의 구분

| 영역 | 기준 | 가격 성격 |
|---|---|---|
| 날씨 | 기상청 단기·중기예보 | 실제 API 정보 |
| 관광지 | VISIT_JEJU 장소·좌표·소개 | 입장료는 수집값 또는 예상값일 수 있음 |
| 지도·이동 | 카카오 지도·카카오모빌리티 | 실제 도로 경로, 장애 시 추정값 보완 |
| 항공 | AeroDataBox 기반 운항 정보 | 운임은 제휴가 없어 현실적인 예상값 |
| 숙소 | 공공 숙박업 원천 + NAVER_HOTEL 상세 연결 | 평균 가격이며 예약 시점과 다를 수 있음 |
| 식당·카페 | 카카오 장소 기반 적재 데이터와 메뉴 | 메뉴 수집 시점 기준 예상 식비 |
| 렌터카 | 실제 차종을 참고한 시연용 데이터 | 업체·가격은 목업 데이터 |
| 자차 | 거리, 평균 연비, 연료 종류, 유가 조합 | 계산된 예상 비용 |

발표에서는 다음처럼 설명하는 것이 가장 정확합니다.

> 장소와 이동 경로, 날씨와 운항 정보는 가능한 범위에서 실제 데이터를 사용했습니다. 다만 항공·숙박·렌터카·식비처럼 제휴와 예약 시점에 따라 변하는 가격은 수집 정보와 현실적인 기준으로 계산한 예상값입니다.

## 9. 현재 검증 상태

- 프론트 자동 테스트 29개 통과
- 제주 대표 명소 15곳의 이름, 고유 ID, 좌표 범위와 일정 요청값 검증
- 애월 카페 거리의 띄어쓰기·행정구역 접두어 호환 검증
- 프론트 운영 빌드와 배포 설정 검사 통과
- 백엔드 전체 테스트 통과
- 운영 번들에 `localhost:8080`이 들어가거나 카카오 지도 키가 빠지면 빌드가 실패하도록 사전 검사
