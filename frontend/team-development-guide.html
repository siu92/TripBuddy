얼마길 개발 기능 가이드

프론트엔드에서 만든 AI 여행 계획 화면을 실제 서비스로 연결하기 위한 팀 공용 설명서입니다. 백엔드·아키텍처·AWS 담당자가 무엇을 만들고, 어떤 결과물을 전달해야 하는지 쉽게 확인할 수 있습니다.

가장 중요한 공통 원칙: 비용은 모두 1인 기준입니다. 숙소·장소를 변경하거나 일정을 생성해도, 같은 선택값이면 화면 전후의 1인 예상 경비는 1원까지 동일해야 합니다.

2. 화면별로 실제 구현되어야 하는 기능

프론트는 이 기능을 보여 줍니다. 백엔드는 각 화면이 사용할 데이터와 계산 결과를 제공해야 합니다.

여행 조건

여행지·세부지역·날짜·인원

국내/해외 여행지를 고르고, 제주도 선택 시 협재·한림 등 세부지역을 추가로 고릅니다.

  • 여행지·세부지역 목록과 이미지
  • 출발일·귀국일, 총인원, 1인 예산 저장
  • 직접 입력한 여행지·지역도 저장
AI 질문 흐름

교통수단 질문과 왕복 항공

출발지 확인 → 항공 여부 → 가는 편 → 오는 편 → 제주 현지 이동수단 순서입니다.

  • 가는 편과 오는 편은 별도 선택
  • 김포/인천 탭, 시간·최저가 정렬
  • 특가, 정가, 할인율, 잔여석 표시
예약 비교

렌터카·숙소 비교

가격만이 아니라 보험, 인수·반납, 취소, 평점·리뷰 수, 객실 잔여 정보를 비교합니다.

  • 숙소: 권역·가격·리뷰·특가 필터
  • 렌터카: 2박 3일 총액과 차량 정보
  • 선택값 즉시 1인 예산에 반영
AI 계획

일정 생성·지도·시간표

AI가 선택한 예약 정보와 테마를 기반으로 날짜별 타임라인, 3일 시간표, 다중 경유지 지도를 만듭니다.

  • 장소별 이동 시간·예상 체류 시간
  • 식당·체험·교통·숙소별 예상 비용
  • 지도에 실제 순서대로 여러 핀과 경로 표시
변경 기능

숙소·장소 변경 후 재설계

숙소 또는 개별 장소를 바꾸면 이전 계획과 다른 새 일정 버전을 생성합니다.

  • 변경 전/후 숙소, 장소, 경비, 이동 시간 비교
  • AI 로딩 상태와 재설계 완료 요약
  • 새 일정은 기존 일정과 구분되는 버전으로 저장
저장·공유

여행 계획 보관 및 공유

생성된 일정은 새로고침 후에도 다시 볼 수 있고, 링크로 팀원에게 공유할 수 있어야 합니다.

  • 여행 초안 저장
  • 최종 일정 저장
  • 읽기 전용 공유 링크

3. 백엔드 개발자에게 전달할 업무

백엔드는 “화면이 사용하는 모든 선택값과 계산 결과를 저장·반환하는 역할”입니다.

1

여행 데이터 저장

  • 여행 초안 생성, 수정, 조회
  • 여행지·세부지역·날짜·인원·예산 저장
  • 항공·숙소·렌터카·테마 선택값 저장
  • 여행 계획 버전 관리
2

비교 상품 데이터

  • 항공: 왕복, 시간, 가격, 특가, 잔여석
  • 숙소: 위치, 가격, 평점, 리뷰, 객실
  • 렌터카: 차량, 보험, 인수·반납, 취소
  • 초기에는 발표용 시드 데이터 가능
3

예산 계산 서비스

  • 개인 비용: 항공·식비·체험 등
  • 공통 비용: 숙소·렌터카·주차비 등
  • 공통 비용은 인원수로 N/1
  • 총액·상세 내역·계산 시각을 함께 반환
4

AI 일정 생성

  • 입력: 날짜, 항공 시간, 숙소, 테마, 속도, 예산
  • 출력: 일자별 일정, 장소 순서, 이동·체류 시간
  • 지도 경유지 좌표와 예상 비용
  • 생성 중/완료/실패 상태 제공
5

변경 재계산

  • 숙소 변경 시 새 일정 생성
  • 장소 변경 시 이후 동선·비용 재계산
  • 이전 계획과 새 계획 비교 데이터 제공
  • 변경 이유와 차이를 짧게 설명
6

저장·공유

  • 내 여행 목록 조회
  • 일정 버전 다시 열기
  • 읽기 전용 공유 링크 생성
  • 공유 권한 및 만료 정책 적용

4. 아키텍처 설계자에게 전달할 업무

아키텍처는 각 기능이 복잡해져도 가격과 일정이 꼬이지 않도록 “길”을 설계하는 역할입니다.

프론트엔드
  • 사용자 선택 화면
  • AI 로딩·결과 화면
  • 지도·시간표·비교 UI
→
API·서비스 계층
  • 여행 관리
  • 가격·예산 계산
  • AI 일정 생성
  • 지도·경로
  • 예약 데이터 어댑터
→
데이터·외부 서비스
  • 여행·사용자 DB
  • 항공·숙소·렌터카 공급사
  • 지도 API
  • AI 모델 API
반드시 정해야 하는 것: 계획·가격 버전
예: 한림리조트 기준 계획은 plan_v1, 히든 클리프로 변경한 계획은 plan_v2로 저장합니다. 각 버전은 선택한 항공·숙소·렌터카·장소와 계산 결과를 함께 갖습니다. 이 구조가 있어야 전·후 비교와 금액 일치를 보장할 수 있습니다.
반드시 정해야 하는 것: AI 생성 상태
AI 일정은 즉시 끝나지 않을 수 있습니다. 따라서 요청됨 → 계산 중 → 완료 → 실패 상태를 API에서 관리해야 프론트의 로딩 화면이 안정적으로 작동합니다.
반드시 정해야 하는 것: 외부 서비스 연결 방식
항공·숙소·렌터카 공급사가 바뀌어도 화면을 고치지 않도록, 각 공급사의 응답을 얼마길 공통 형식으로 변환하는 어댑터를 둡니다. 실제 제휴 전에는 같은 형식의 시드 데이터를 사용합니다.

5. AWS·인프라 담당자에게 전달할 업무

인프라는 사용자가 언제 접속해도 안전하게 화면과 API를 이용하게 만드는 역할입니다.

1

웹사이트 배포

  • React 결과물을 S3 + CloudFront 또는 Amplify에 배포
  • 도메인 연결과 HTTPS 인증서 적용
  • 개발·시연·운영 주소 분리
2

서버·데이터베이스

  • API Gateway + Lambda 또는 ECS/Fargate 선택
  • 여행·사용자·일정·견적 데이터 DB 구축
  • 이미지와 첨부 파일은 S3 저장
3

보안·운영

  • 외부 API 키는 Secrets Manager에 보관
  • IAM 최소 권한, HTTPS, WAF 적용
  • CloudWatch 로그·오류·비용 알림

6. 프론트엔드가 요청하는 API 목록

정확한 주소는 백엔드 팀이 정해도 됩니다. 아래처럼 “무슨 일을 하는 API인지”가 명확해야 합니다.

POST /trips — 여행 초안 생성

PATCH /trips/{tripId} — 여행 조건·선택값 수정

GET /destinations — 국내/해외 여행지와 세부지역 목록

POST /quotes/flights — 가는 편/오는 편 항공 비교

POST /quotes/stays — 숙소 필터·정렬·비교

POST /quotes/rentals — 렌터카 비교

POST /budgets/calculate — 1인 기준 예산 계산

POST /plans/generate — AI 일정 생성 작업 시작

GET /plans/{planId}/status — AI 생성 진행 상태·결과 조회

POST /plans/{planId}/revisions — 숙소/장소 변경 후 일정 재설계

POST /trips/{tripId}/share — 공유 링크 생성

7. 구현 우선순위와 완료 기준

처음부터 실시간 예약까지 만들 필요는 없습니다. 발표용 시연 데이터 → 실제 데이터 연동 순서로 진행하면 됩니다.

1단계 · 시연 가능 MVP
여행 저장, 발표용 항공·숙소·렌터카 데이터, 1인 예산 단일 계산, AI 일정 결과 저장
2단계 · 기능 연결
AI 생성 비동기 처리, 지도 다중 경유지, 숙소·장소 변경 재계산, 공유 링크
3단계 · 실제 서비스화
실시간 공급사 데이터, 제휴 예약, 결제, 사용자 로그인, 알림 기능
완료 확인 기준
같은 선택값이면 어느 화면에서도 1인 총액이 동일하고, 변경 후에는 새 버전의 일정·지도·경비가 함께 바뀝니다.

8. 역할별 상세 작업 안내 — 처음 맡는 사람도 이 순서대로 진행하세요

아래는 “무엇을 만들지”뿐 아니라 “완성한 뒤 누구에게 연결해야 하는지”까지 적은 실무용 안내입니다.

먼저 이해할 단어 5개
프론트엔드는 사용자가 보는 화면입니다. 백엔드는 화면의 요청을 받아 계산·저장·조회하는 서버입니다. 데이터베이스(DB)는 여행과 일정 정보를 오래 보관하는 저장소입니다. API는 프론트와 백엔드가 대화하는 약속입니다. 클라우드 인프라는 이 화면·서버·DB를 인터넷에서 안전하게 실행시키는 AWS 환경입니다.
A. 클라우드 아키텍처 담당자 — 반드시 만들어야 할 구성과 연결 방식

목표: 사용자가 주소로 접속하면 프론트 화면이 열리고, 프론트가 안전하게 백엔드 API를 호출하며, 여행 데이터가 DB에 저장되는 환경을 만드는 것입니다.

1. 사용자 브라우저
  • 얼마길 웹사이트 접속
  • 여행 조건 입력
  • 일정·경비 확인
→
2. 프론트 배포 영역
  • Route 53: 도메인 연결
  • ACM: HTTPS 인증서
  • CloudFront: 빠른 전달
  • S3: React 화면 파일
→
3. 백엔드·데이터 영역
  • API Gateway: API 입구
  • Lambda/ECS: 서버 코드 실행
  • RDS: 여행·일정 DB
  • S3: 이미지·공유 파일

반드시 들어갈 AWS 구성:

  • Route 53 + ACM + CloudFront + S3: 사이트 주소, HTTPS 보안 연결, 빠른 화면 전달, React 배포 파일 보관을 담당합니다. 사용자의 첫 접속 경로입니다.
  • API Gateway: 프론트가 /trips, /plans/generate 같은 요청을 보내는 공식 입구입니다. 요청 횟수 제한과 CORS 설정도 여기서 처리합니다.
  • Lambda 또는 ECS/Fargate: 실제 백엔드 코드를 실행합니다. 발표·MVP 단계에서는 관리 부담이 적은 Lambda가 적합하고, 장시간 AI 처리나 복잡한 서버가 필요해지면 ECS/Fargate를 고려합니다.
  • RDS PostgreSQL: 사용자, 여행 초안, 항공·숙소 선택, 예산, 일정 버전을 저장합니다. DB는 외부 인터넷에서 직접 열지 않고 서버만 접근하도록 둡니다.
  • S3: 숙소·관광지 이미지, 공유용 파일처럼 큰 파일을 보관합니다. DB에는 파일 자체가 아니라 S3 주소만 저장합니다.
  • Secrets Manager: 지도 API, AI API, 항공·숙소 제휴 API의 비밀 키를 보관합니다. 키를 GitHub나 프론트 코드에 넣으면 안 됩니다.
  • CloudWatch: 서버 오류, AI 생성 실패, 느린 API, 비용 이상을 확인하고 알림을 받습니다.
  • IAM + WAF: 서비스끼리 필요한 권한만 주고, 비정상적인 외부 요청을 차단합니다.

아키텍처 담당자가 백엔드 팀에게 넘길 것: 개발/시연/운영 환경 주소, DB 접속 방식, API 실행 방식, 환경변수 이름, 로그 확인 위치, 배포 권한 규칙.

B. 백엔드 담당자 — 화면 기능을 실제 데이터로 바꾸는 작업

목표: 프론트의 버튼 클릭이 실제 데이터 저장·조회·계산으로 이어지게 만드는 것입니다. 처음에는 실제 예약사 연동 대신 발표용 데이터로 시작하고, 응답 형식은 실서비스와 같게 만듭니다.

반드시 만들어야 하는 데이터 묶음:

  • 사용자(User): 사용자 ID, 이름, 로그인 정보. 로그인 기능이 아직 없으면 임시 사용자 ID로 시작해도 됩니다.
  • 여행 초안(Trip): 여행지, 제주 세부지역, 출발일·귀국일, 인원, 1인 예산, 테마, 여행 속도를 저장합니다.
  • 선택 상품(Selection): 가는 항공편, 오는 항공편, 렌터카, 숙소의 선택 ID와 가격·선택 시각을 저장합니다.
  • 견적(Quote): 정가, 할인가, 할인율, 잔여석/객실, 평점·리뷰 수, 기준 시각을 저장합니다. 화면에는 ‘현재 기준 시연 데이터’ 표시가 필요합니다.
  • 일정 버전(Plan Version): AI가 만든 일정을 v1, 숙소 변경 후 일정을 v2처럼 보관합니다. 변경 전/후 비교의 기준입니다.
  • 일정 항목(Itinerary Item): 날짜, 시작 시각, 장소명, 좌표, 이동 시간, 체류 시간, 예상 비용, 장소 유형을 저장합니다.

가장 중요한 계산 규칙: 프론트에서 임의로 합산하지 않고, 백엔드의 예산 계산 함수 한 곳에서만 계산합니다. API는 `1인 총액`, `개인 비용`, `공통 비용 총액`, `공통 비용의 1인 분담금`, `계산 시각`, `계산 버전`을 함께 반환합니다. 그래야 숙소 선택 화면의 801,800원과 일정 화면의 금액이 달라지는 문제가 사라집니다.

AI 일정 생성 로직의 입력과 출력:

  • 입력: 출발·귀국 날짜와 항공 시간, 숙소 위치, 인원, 예산, 테마, 여행 속도, 렌터카 여부, 이미 선택한 장소.
  • 출력: 3일치 시간표, 장소 순서, 각 구간 이동 시간, 지도 경유지 좌표, 항목별 1인 비용, 전체 1인 총액, 추천 이유.
  • 변경: 숙소를 한림에서 중문으로 바꾸거나 폭포를 카페 거리로 바꾸면, 이후 일정만 새로 배치하고 기존 버전과 달라진 시간·비용·동선을 반환합니다.

백엔드 담당자가 프론트 팀에게 넘길 것: Swagger 또는 Postman API 문서, 테스트 서버 주소, API별 요청·응답 예시, 오류 코드 목록, 테스트용 여행 ID.

C. 아키텍처 설계자 — 서비스가 커져도 금액과 일정이 꼬이지 않게 설계

목표: 항공·숙소·렌터카·AI·지도 기능이 서로 섞여 망가지지 않도록 각 역할을 분리하고 데이터가 흐르는 길을 정하는 것입니다.

  • 여행 관리 서비스: 사용자가 고른 여행 조건과 선택 상품을 보관합니다.
  • 가격·예산 서비스: 모든 항목의 1인 비용을 계산합니다. 다른 서비스는 총액을 직접 수정하지 않습니다.
  • 상품 비교 서비스: 항공·숙소·렌터카 공급사 응답을 얼마길 공통 형식으로 바꿉니다.
  • AI 일정 서비스: 여행 조건을 받아 일정을 생성합니다. 생성 시간이 길 수 있으므로 작업 ID와 진행 상태를 관리합니다.
  • 지도·경로 서비스: 일정 장소의 좌표와 이동 경로를 지도 API 형식으로 제공합니다.
  • 공유 서비스: 여행 계획을 읽기 전용 링크로 공개할 수 있게 합니다.

꼭 정해야 할 연결 규칙:

  • 항공·숙소·렌터카를 선택할 때마다 여행 초안을 수정하고, 예산 계산 서비스를 다시 호출합니다.
  • AI 일정 생성은 선택값이 확정된 여행 초안의 스냅샷으로 실행합니다. 실행 중 값이 바뀌어도 기존 작업 결과가 섞이지 않습니다.
  • AI 완료 결과는 새 일정 버전으로 저장하고, 같은 버전의 예산 결과를 화면에 보냅니다.
  • 외부 항공·숙소 API가 실패하면 마지막 캐시 데이터 또는 ‘현재 비교 데이터를 불러올 수 없습니다’ 안내를 보여 줍니다.

아키텍처 담당자가 팀에 남길 문서: 전체 구조도, DB 관계도, API 규칙, 서비스 간 호출 순서, 실패·재시도 규칙, 개인정보·권한 정책.

D. 프론트엔드 담당자 — 백엔드가 연결되면 해야 할 일
  • 현재 더미 데이터를 API 호출 결과로 교체합니다. 화면 디자인과 사용자 흐름은 유지합니다.
  • API가 ‘계산 중’일 때 AI 로딩 화면을 보여 주고, 실패 시 다시 시도 버튼과 쉬운 안내 문구를 보여 줍니다.
  • 서버가 준 1인 총액과 상세 비용만 표시합니다. 프론트에서 별도의 금액 합계를 다시 만들지 않습니다.
  • 여행 ID와 일정 버전을 주소 또는 상태에 저장해 새로고침 후에도 같은 여행을 다시 열 수 있게 합니다.
  • 개발 서버·시연 서버·운영 서버의 API 주소를 환경변수로 구분합니다.

프론트 팀이 받아야 시작할 수 있는 것: API 주소, 로그인 방식, API 문서, CORS 허용 주소, 이미지 URL 규칙, 오류 응답 형식.

E. 팀이 함께 확인해야 하는 최종 점검 목록
  • 같은 여행 조건·선택 상품이면 숙소 화면, 예산 화면, 일정 화면의 1인 총액이 동일한가?
  • 가는 편과 오는 편 항공은 별도 저장되며, 선택한 출발·도착 시간이 AI 일정 시작·종료 시간에 반영되는가?
  • 숙소 또는 장소를 바꾸면 새 일정 버전, 지도 경로, 시간표, 비용이 함께 바뀌는가?
  • AI 생성 중에는 로딩 상태가 보이고, 실패해도 사용자가 현재 선택값을 잃지 않는가?
  • API 키와 DB 비밀번호가 코드·GitHub에 노출되지 않았는가?
  • 시연 주소에서 누구나 프론트를 열 수 있고, 백엔드 오류는 담당자가 로그에서 찾을 수 있는가?

“프론트는 사용자 흐름과 화면을 완성했습니다. 백엔드는 여행 선택값·예약 비교·1인 예산·AI 일정 재생성을 API로 제공하고, 아키텍처는 계획 버전과 가격 일관성을 설계하며, AWS는 배포·보안·로그·자동 배포 환경을 구축해 주세요.”
