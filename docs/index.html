01 / 문제 발견과 조사

여행 준비의 불편을 조사하고,
해결할 과제를 찾았습니다

여행은 좋았지만,
매번 일정을 짜는 일은 번거로웠습니다.

여행을 준비할 때마다 갈 곳과 식당을 찾고, 지도에서 이동시간을 확인한 뒤 하루 일정으로 엮었습니다. 숙소와 교통편까지 맞추고 나면, 여행 하나를 위해 여러 서비스와 정보를 오가야 했습니다.

이 불편이 저만의 경험인지 확인하고 싶었습니다. 공개 조사와 여러 여행 서비스, 매체와 이용 후기를 검토하며 사람들이 어느 과정에서 어려움을 겪는지 살폈습니다.

  2. 02 · 조건과 동선 확인

    하루 일정으로 직접 맞췄습니다

    영업시간과 위치, 이동시간을 대조해 방문 순서를 정해야 했습니다.

  3. 03 · 여행 중 변경

    변수 하나에 다시 조율했습니다

    식당 휴무나 날씨 변화가 생기면 대체 장소와 남은 동선을 다시 찾아야 했습니다.

02 / 기존 서비스 검토

일정을 추천받은 뒤에도,
직접 고쳐야 하는 수고가 남았습니다

여행 상품 비교와 AI 일정 추천은 이미 제공되고 있었습니다. 저는 여러 자료를 살펴보며, 만들어진 일정을 실제 여행 조건에 맞게 수정하는 과정에 해결할 여지가 있다고 봤습니다.

트리플 · App Store 이용 후기

장소 추가와 날짜별 편집의 불편

등록되지 않은 장소를 넣거나 날짜별 일정을 편집할 때 불편을 겪은 이용 사례를 확인했습니다.

Trip.com · 개별 사용 후기

일정판에서 시작 시각 수정에 제약

AI 프롬프트로 시각을 지정할 수 있어도, 일정 화면에서 바로 고치는 과정에는 제약이 있다는 사례가 있었습니다.

인용 후기 원문

폭넓게 검토한 자료 중 발표에 사용한 사례입니다. 개별 후기를 모든 사용자나 현재 서비스 전체의 문제로 일반화하지 않았습니다.

제가 정한 해결 과제

일정을 만들어주는 데서 그치지 않고,
여행 중 바뀐 계획도 직접 조정할 수 있게 만들자.

03 / 완성한 서비스

일정 생성과 여행 중 수정을
하나의 서비스로 연결했습니다

이 과제를 팀과 함께 TripBuddy로 구체화했습니다. 예산과 여행 조건을 입력하면 일정을 만들고, 결과 화면에서 장소와 방문 순서를 직접 바꿀 수 있도록 구현했습니다.

  1. 01여행 조건 입력

    예산·날짜·교통·숙소·취향

  2. 02AI 일정 생성

    조건을 반영한 날짜별 계획

  3. 03일정 직접 수정

    방문 순서 변경·장소 교체

  4. 04여행 중 활용

    모바일에서 일정·경로 확인

① 날짜와 예상 경비현재 여행 조건과 비용을 확인합니다.

② 일정 편집장소를 교체하고 방문 순서를 바꿉니다.

③ 이동 경로변경된 일정의 동선을 함께 살핍니다.

04 / 팀이 구현한 프로젝트 전체

화면·백엔드·클라우드·배포를
하나의 서비스로 완성했습니다

사용자가 조건을 입력하면 서버가 실제 장소 후보를 선별하고, AI 생성 결과를 검증해 화면에 전달합니다. 저는 프론트엔드와 PM 역할로 이 흐름을 각 담당자와 맞췄습니다.

BACKEND · 팀 구현

실제 후보를 선별하고,
AI가 만든 일정을 검증했습니다

Java·Spring Boot 서버에서 공공데이터와 항공·날씨·경로 API를 연결해 여행 정보를 확보했습니다. 서버가 조건에 맞는 장소 후보를 좁히고, Bedrock은 그 안에서 방문 순서를 제안하도록 구성했습니다.

결과의 장소 ID·중복·누락을 검사하고, 생성 실패 시 서버 규칙으로 대체 일정을 구성했습니다. 일정 편집 뒤에는 바뀐 날짜의 경로와 이동비를 다시 계산했습니다.

제가 연결한 부분
백엔드 담당자와 요청·응답 형식과 생성 상태를 맞춰, 입력부터 결과·편집까지 화면에 연결했습니다.

AWS CLOUD · 팀 설계·구현

일반 API와 긴 AI 작업을
분리해 실행했습니다

정적 화면은 S3·CloudFront로 제공하고, API와 Worker는 EKS의 별도 실행 단위로 나눴습니다. 오래 걸리는 생성 요청은 SQS를 거쳐 Worker가 처리하도록 했습니다.

최종 일정은 RDS MariaDB에 저장하고, 반복 조회는 ElastiCache Redis와 TTL로 재사용했습니다. IAM 역할과 Secrets Manager로 접근 권한·민감정보를 분리했습니다.

제가 연결한 부분
클라우드 담당자와 배포 환경의 API 연결을 확인하며, 사용자 요청부터 클라우드 처리 결과까지 이어지는 구조를 경험했습니다.

DEVOPS · 팀 배포·운영 검증

변경한 코드를 배포하고,
부하에 따른 확장·축소를 확인했습니다

프론트엔드는 GitHub Actions 빌드 후 S3에 배포하고 CloudFront 캐시를 갱신했습니다. 백엔드는 빌드·테스트와 Docker 이미지 검사를 거쳐 ECR·Argo CD·EKS로 반영했습니다.

부하 테스트에서는 API Pod의 CPU 부담을 관찰하고, HPA로 Pod가 늘어난 뒤 부하 감소 시 다시 줄어드는 동작을 확인했습니다.

제가 연결한 부분
화면 변경과 백엔드·배포 작업의 진행 상황을 맞추고, 배포된 서비스의 시연과 프로젝트 마무리를 준비했습니다.

위 내용은 팀 전체의 핵심 구현입니다. 프론트엔드는 제가 담당했고, 백엔드·AWS·DevOps는 각 담당자와 협업했습니다. 부하 테스트 결과를 실사용자 성과나 실제 AWS 비용 절감액으로 바꾸어 표현하지 않았습니다.

06 / 판단을 구현으로 옮긴 사례

설계한 흐름을 실제 화면과 동작으로 만들었습니다

CASE 01 · 입력 흐름

예산을 먼저 받아
이후 선택의 기준으로 삼았습니다

교통편과 숙소를 각각 고른 뒤 비용을 맞추는 대신, 여행의 예산을 첫 단계에서 정하도록 설계했습니다.

예산 → 출발지·목적지 → 날짜 → 교통·숙소 → 취향 순서로 필요한 조건을 확보했습니다.

조건 입력 시연
CASE 02 · 설계 수정

출발시각을
필요한 경우에만 물었습니다

처음에는 날짜와 시간을 함께 받았지만, 항공·KTX는 티켓 시각이 일정 기준이 됩니다. 공통 날짜 화면에서 시간 입력을 빼고 자차를 선택한 경우에만 설정하도록 바꿨습니다.

모든 사람에게 같은 정보를 묻던 흐름을 교통수단에 맞춘 입력으로 수정했습니다.

CASE 03 · 프론트엔드와 API

AI 생성 상태를
화면의 대기·완료·오류로 연결했습니다

요청을 보낸 뒤 결과가 올 때까지의 흐름도 화면의 일부로 다뤘습니다. API의 처리 상태를 확인해 대기와 결과를 구분하고, 공통 인증·세션·오류 처리를 재사용하도록 연결했습니다.

사용자의 입력부터 API 요청, 생성 상태 확인, 결과 화면까지 하나의 흐름으로 구현했습니다.
